# The Agent Ledger — Shared Sources Prompt

Use this prompt together with either an edition prompt. It defines the
publication's shared subject scope and research standards; the selected
edition prompt defines its time window, format, and length. Use
agent-ledger-source-registry.md as a living shortlist when it is
available. The registry is a discovery aid, not an endorsement or
substitute for checking evidence.

## Editorial Scope

Cover meaningful advances in:
- LLM models: capabilities, reasoning, multimodality, efficiency,
  inference cost, context, and open-weight releases.
- Agents: tool use, planning, memory, autonomous workflows,
  coordination, and demonstrated task performance.
- Agent harnesses: execution loops, sandboxes, context management,
  orchestration, permissions, evaluation, tracing, and reliability.

Also flag relevant upcoming technical events and deadlines.

## Discovery

Start with relevant sources in the source registry, but discover new
candidates as well. Use a balanced mix of:
- Hacker News.
- Official research and engineering blogs, model cards,
  documentation, release notes, and GitHub releases.
- arXiv, Hugging Face Papers, and OpenReview.
- Independent evaluations and reputable technical reporting.
- Curated technical sources such as Simon Willison, Latent Space,
  and The Batch.

Use discussion forums and newsletters for discovery and context, not as
proof. Do not rely on any one source category or publication when
stronger or independent evidence is available.

## Curating Sources

Treat a source as a lead, not as proof. When a new source repeatedly
surfaces relevant work:
- Record its name, canonical URL, topic areas, source type, practical
  use, last-reviewed date, and status in
  agent-ledger-source-registry.md.
- Mark new entries as **Candidate**. Trial them across two edition
  cycles before marking them **Active**; promote only if they produce
  relevant, verifiable leads that add coverage beyond the existing
  registry.
- Keep useful but inconsistent sources as **Watch**. Mark inactive,
  low-signal, or redundant sources **Retired** instead of silently
  deleting their history.
- Recheck active entries periodically and update the last-reviewed
  date. Remove broken or materially changed URLs, or record a corrected
  canonical URL.

Do not add a source just because it is popular or reported one
interesting story. Verify specific claims against primary evidence
regardless of registry status.

## Verification and Attribution

- Verify important claims against original evidence where available.
- Prefer direct links to announcements, papers, code, documentation,
  evaluations, demos, and official event pages.
- Clearly distinguish shipped releases, previews, research findings,
  and evaluations.
- Label vendor-reported results and unreviewed research.
- Do not compare benchmark results gathered under incompatible
  conditions.
- Use original publication or release dates to determine freshness,
  not the date a story was discussed or republished.
- Never invent quotations, dates, availability, or performance claims.
- If browsing or source access is unavailable, disclose the limitation
  and do not invent current news.

Keep sourced facts, reported claims, and editorial interpretation
distinct. Prefer concrete capability changes, useful releases, and
credible results over funding news, teasers, speculation, and minor
updates. Popularity is a discovery signal, not proof of quality.
